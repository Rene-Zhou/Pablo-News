### 2. 🔥 Linus Torvalds 发布首个 LLM 辅助的内核补丁系列：10 个补丁重构 folio 查找、读密集基准提速一个数量级——评审已发现竞态条件（HN 109 分、84 条评论）

### 5. Show HN：Parsimony——开源基准"哪个 AI 编码 agent 改动最少"：净编码单元数=新增−删除，不数行数所以"塞代码"没用（HN 76 分、17 条评论）

**开发者 lasu 发布开源基准 Parsimony：现有基准只测解题率与 token 成本，不惩罚多余代码——而多余代码会让代码库长期更难维护。Parsimony 复用各基准已公开的补丁（DeepSWE、SWE-bench Verified、SWE-bench Live），统计"编码单元"数：语句、调用、比较、名字、字面量等语法元素。不按行数计，压缩写法得不到奖励；删除的代码会被减去——净单元数 = 新增 − 删除。模型按"已解题任务的平均净新增单元"升序排名。**

**关键细节：**
- 方法学自曝一处诚实校准：GPT-5.6 Sol 用两种方式各跑一遍，自跑版本新增代码为公开版本的 0.88 倍
- fastfall 的实战评论最有信息量："完全同意该测并削减 LLM 灌进代码库的废话，但 Astra 在这个榜上'赢'对我不是好信号——Astra 玩的是代码高尔夫，产出的代码基本不可读。我自己的显示偏好是宁可要 Claude 那种过量的注释和测试，也不要那种不可读"
- KasianFranks 的反对意见代表另一端："一旦大家理解向量空间的真正规模，没人会在乎 AI 生成了多少代码——复杂度对 AI 系统不是问题"；Vakaiser 的求救帖则来自一线："谁有办法降低 agent 生成代码的复杂度和冗余度？"
- Xeoncross 的基准民主化诉求：希望所有 AI 基准都用普通人能在本地跑的最强模型（当前是 Qwen 3.8 27B，Q4 约 28GB 内存），"我想知道开放权重离商业前沿到底多近"

### 7. 《Your Game Is A Harness》：15 年游戏程序员的 LLM 实战长文——"LLM 擅长 Web 栈、搞不定游戏"的根因是游戏大量内容不是代码，让游戏对 agent"可读"才是正解（HN 164 分、85 条评论）

**游戏开发者 Kyle Kukshtel 把他在 Indie Rodeo（卡尔加里）的 45 分钟演讲整理成文（全文 100% 手写，他特意声明）：核心论点是"LLM 在 Web 栈上几乎无所不能，但每次用于非 Web 的游戏项目就翻车"。原因有三：高质量开源游戏代码的训练数据比 Web 少几个数量级；游戏有大量非代码资产（美术、动画、手感），这些对 LLM 完全不透明；如果游戏依赖对这些不透明物的操纵，agent 必然失灵。解法不是等模型变强，而是把游戏工程改造成对 agent 可读的"harness"（驾驭具）。**

**关键细节：**
- 文中对"context pollution"（上下文污染）的讲解被 HN 读者称道：每次发消息，历史消息都会被整体重发，"就像 playground 游戏——轮到你时必须先复述所有人之前的东西再加自己的"，所以坏输出会持续污染后续工作，管理上下文是使用 LLM 的核心技能
- 对 Three.js 一次性生成游戏现象的解释很锋利："那类东西之所以是 slop，是因为缺乏 LLM 中位数之外的作者声音"——把一切表示为代码（盒子几何体）恰好绕开了非代码资产的缺口
- 文章同时是方法论：如何让游戏对 AI agent 更"可读"、如何加速 agent 迭代循环——标题即立场：你的游戏本身就该被当作 harness 来设计
- 连续性：与 Parsimony（今日模型板块）、Anthropic 源码控制重构（10/14）互为补充——大厂在重构基础设施适应 agent，独立开发者在重构"作品"的形态适应 agent；两条路线本周首次同框

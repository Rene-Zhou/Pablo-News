### 1. 🔥 Apiiro 审计：Claude Code 的"Don't ask again"把密码直接写进 GitHub——公开仓库中 104,185 份 `.claude/settings.local.json` 里 1,122 份含真实机密，合计 2,539 条真实密钥（数据库密码、云密钥、SSH root 登录）散落在 1,994 个仓库，63 家组织暴露，其中 539 个仓库里"提交该文件的 commit 由 Claude 共同署名"；Claude Code 负责人 Boris Cherny 周末现身 HN："我们正在研究能做什么来预防"，承诺原型化"自动模式捕获 + 基础密钥扫描"（HN 538 分、382 条评论）

安全公司 Apiiro 11/5 发布、周末引爆的研究还原了完整的泄露链路：开发者机器上有连接串、云密钥、API token；让 Claude Code 查数据库或调 API 时，它提出的命令必然带着机密；第 N 次弹窗后你点了"Yes, and don't ask again"——于是**那条原样包含机密的命令字符串被存进项目目录下的 `.claude/settings.local.json`**，随后与代码一起被 commit、被 push。GitHub 上该文件的公开副本有 104,185 份（分布于 103,617 个仓库），1.1% 含真实机密；另有 1,160 条藏在 git 历史、团队有意提交的 `settings.json` 与误传的 agent 聊天记录里。最受关注的组织级案例：一家数据库厂商自己的管理员级云密钥、一家 B2B 初创的生产 Azure Postgres 密码、一家软件代理公司的 Square 生产 token、一家医疗记录应用云数据库的 owner 密码；43 条公网服务器 SSH 凭据中有 root 密码（`sshpass` 命令形式）。

**关键细节：**
- Apiiro 强调"这是 Claude Code 自身的行为，不是模型的"——用 Opus 5.5 与 Fable 5.1 均复现；Claude Code 创建该文件时会把它加进开发者**全局** gitignore，但不写入仓库自身的 .gitignore；文件一旦已被 git 追踪，后续批准还会继续追加进去，用户不会被提示
- 最刺眼的统计：1,105 个含真实机密的可追溯仓库中，539 个有"Claude 共同署名"的 commit 改动过该文件——Claude Code 的提交指引禁止 commit `.env` 与 credentials.json，**但它自己的设置文件不在清单上**
- Boris Cherny（Claude Code 负责人）11/7 起在 HN 回应：历史上 Claude Code 未做密钥清洗（"有很多好工具干这个"），但"我们正在研究能做什么来预防"，将原型化让 auto mode 捕获此类情况、内置基础密钥扫描；有读者指出 auto mode 同样可能中招，他回复"good catch"
- HN 评论区的纠偏同样值得记录：Aurornis 指出标题有歧义——点"Don't Ask Again"本身不泄露密码，还需要"手动创建该文件、批准含机密的命令、再公开仓库"三连；rvz 的反面观点被反复引用："这种事若发生在开源 harness 里早被抓住了——闭源 harness 内部做了什么你无从知晓"
- 连续性：与 Claude Code 把邮箱写进 User-Agent（11-07 第 1 条）构成一周内的第二起 Claude Code 隐私/安全事故——上周是 harness 把身份信息发给第三方网站，本周是 harness 把机密留在公开仓库；与 Apple 知识图谱（11-08 第 2 条）同属"工具默认行为 vs 用户知情"主线，但这一起的修复承诺已官方落地

## 模型与基础设施

### 5. Show HN：llama-modchip——把 284B 的 DeepSeek-V4-Flash（284.33B 总参/13.17B 激活）压到 1.71 bpw、56.56 GiB，塞进 64GB 内存零 GPU 运行，16 核 Zen 5 上预填 44.36 tok/s、生成 9.1–14.7 tok/s；antirez 实测 128GB 统一内存"编码 agent 可用速度"、预填约 300 t/s；评论区最大争议是 2-bit 以下量化的质量代价——"4-bit 是体积-性能比的峰值，更低会显著掉性能"（HN 292 分、104 条评论）

llama-modchip v2.4.0（Apache 2.0）是一套 ggml/llama.cpp 内核补丁 + 量化转码器 + 运行时工具，让稀疏 MoE 检查点完全跑在系统内存里，覆盖 x86_64（AVX-512/AVX2）与 ARM64（NEON/SVE/Apple Metal）。核心工程：标准 UD-IQ1_S 构建的 DeepSeek-V4-Flash（43 层 MLA + 256 个路由专家）占 76.87 GiB 装不进 64GB，他们把它压到 1.71 bpw = 56.56 GiB，峰值 VmRSS 57.61 GiB（256K 上下文）、零 NVMe swap；KV 槽经 /dev/shm 恢复仅需 13.1 ms。三档硬件定位：16–32GB 笔记本跑 Nemotron-3.5-30B-A3B（3.75 bpw，25–60 tok/s）；64GB 台式机跑 284B DeepSeek（9.1–14.7 tok/s 生成）；CPU + 16GB GPU 混合（热 attention 层上 GPU、冷专家驻内存）80.8 tok/s；128GB Threadripper 八通道 DDR5 饱和带宽跑 30B 达 111.62 tok/s。

**关键细节：**
- antirez 的跟帖给了它最重的背书："用 128GB 统一内存跑甚至更快——编码 agent 可用速度，预填约 300 t/s，大段预填还能更快"（他贴出 X 实测链接）
- 质量怀疑派同样强势：walrus01——"我重度用过 deepseek v4 flash 0731，对'这个体积还能出好结果'极度怀疑，那个尺寸的模型要约 150GB 内存才能正经跑"；armcat 引经验数据"量化峰值在 4-bit，再往下性能显著下降"；akie 的第一问即"哪个量化档？只想知道这个"
- 工程美观度的小插曲：intoXbox 批评 README 是"AI slop 式的烦人排版"，superkickstart 跟进"求清理 emoji"——README 本身成了 AI 生成内容的展品
- 同主题轻量补充：Show HN Maple（19 分）——Sub-2-BPW 的 MoE 剪枝，让 Gemma 4 26B 在 6GB GPU 上跑 45 TPS，与本项目同属"极端量化跑消费硬件"路线
- 连续性：与 Revolut 自托管 GLM（11-07 第 6 条）、ERNIE 5.5 Flash Base（11-06 第 5 条）、HyperFlow H3 Flash（11-08 第 5 条）同线——"把前沿模型塞进消费级硬件"正在从单点项目长成品类；而当 RAM Altman（今日第 8 条）在嘲讽"闲置内存"时，这个项目正是闲置内存的最好用途

## AI 应用与产品

### 6. "Agent memory 需要它的 OpenTelemetry 时刻"：一份对编码 agent 记忆格式碎片化的清点——AGENTS.md/CLAUDE.md、.cursor/rules、Anthropic 记忆工具的 /memories 目录、Copilot 存在 GitHub 侧的仓库事实、MCP 服务器的 JSONL 知识图谱，"四种形状，互相都读不了"；"缺的不是工具，是共识"（HN 152 分、100 条评论）

## 研究与突破

### 11. Q Labs《Quadrillion-parameter transformers and how to train them》：人类约 100 万亿突触参数只看约 2 亿 token（1:500,000），Chinchilla 给 30T token 的处方是 1.5 万亿参数（20:1）——"按此我们该训的是百万亿亿（quintillion）参数网络，现在的网络小了七个数量级"；数据集固定时计算最优参数量随算力预算持续增长，外推到 5T token、10²⁹ FLOPs 时集成需 300+ 参数/token，约为 Chinchilla 处方的 7,000 倍——⚠️ 本报补录：HN 提交约在 11/03，属 11-04 早报窗口内漏收，核对从未见报后补入（arXiv 2610.37842，HN 64 分、57 条评论）

Baron et al. 2026 的核心挑衅在引言第一段：AI 与人类之间 100 万倍的样本效率差距是领域中心谜题之一，而模型大小是线索——把每个突触算作一个权重，人类是"参数极大、数据极少"的学习器；Chinchilla 是"参数适中、数据极多"。为弥合 tokens-per-parameter 的 10,000,000 倍差距，"我们应该训练的是 quintillion 参数网络"。方法上，团队在固定数据集上跨数据规模、模型规模、epoch 数训练 transformer，拟合损失对各因素的依赖（含过拟合项与 snapshot ensembling 集成项），发现：数据集固定时，计算最优模型尺寸随算力预算持续增长——且应同时增加 epoch 数与集成成员数；这与 Chinchilla"固定 20 token/参数"的处方在多 epoch 数据受限 regime 下分道扬镳。外推：5T token、10²⁹ FLOPs 时集成总参数超 300/token，约 7,000 倍于 Chinchilla 比率，且随算力继续增长。

**关键细节：**
- 现实注脚：这解释了为什么它目前停留在"处方"阶段——quadrillion 参数即使 1-bit 量化也是 100+ TB 量级；论文的价值在于给出 scaling law 的另一极（参数轴而非数据轴），与"数据墙"叙事（后训练公地枯竭，11-05 第 14 条）互为镜像：数据不够时，参数与多 epoch 是剩下的两个旋钮
- 连续性：与 METR 报告"确信 Anthropic 的加速并非来自训练算力扩容"（11-08 第 1 条）放在一起读格外有趣——若本文的 law 成立，行业在参数轴上的投入不是太多而是差七个数量级，"scaling 已死"与"scaling 才刚开始"的争论又多了一块砝码；与 Modchip 的 1.71 bpw（今日第 5 条）构成谱系两端的黑色幽默：一端在把 284B 压进 64GB 内存，另一端在论证该训 10¹⁵ 参数

### 1. 🔥 PHP 紧急安全更新"PHP2Shell"：两个未认证 RCE 横跨近十年全部版本——AI 找到的漏洞、提前破裂的 embargo、把自己官网都下线的荷兰网安中心（四条 HN 讨论串合计 2600+ 分）

**PHP 官方 10/21 发布 8.5.12、8.4.27、8.3.36、8.2.35 四个维护版本，修复两个 critical 漏洞：CVE-2026-109618（OOM 内存损坏——请求恰好在 memory_limit 临界点耗尽内存时，PHP 可能留下部分初始化的内部数据并事后当作有效数据使用；Apache mod_php 下无需认证、应用代码运行前即可触发，默认配置已演示完整远程代码执行，PHP-FPM 亦经应用级路径确认）与 CVE-2026-109619（陈旧状态——致命错误的时机不巧会让内部状态指向上一请求的内存，同一 worker 的后续请求随即使用已释放内存；报告者对一个真实在线应用演示了 RCE）。Wiz 将其命名为 PHP2Shell 并给出量级判断：PHP 驱动全球约 70% 的网站（WordPress、Joomla、Drupal、Wikipedia 的 MediaWiki），"近十年发布的每个 PHP 版本至少中一条，可追溯到 5.4"，这批发现"属于 PHP 乃至软件史上最严重之列"。**

**关键细节：**
- Wiz 的定性是全案的题眼："底层缺陷已存在数十年，但证明其可利用需要一条异常复杂的链——处在人类研究员实践能力边缘。前沿 AI 模型大幅降低了这道门槛，把一个长期沉睡的缺陷变成可用的 exploit。"发现方 Calif 使用 GPT-5.6 Sol（经 OpenAI 的 Patch the Planet 计划，见第 2 条），Wiz 则独立发现并报告了两个漏洞
- Embargo 提前破裂的全过程（PHP 安全团队成员 Alexandre Daubois 的复盘）：10/20 一条引用"可靠来源"的匿名 HN 帖出现即被删除，但截图已传遍 X 与 Mastodon；署名 Calif.IO 的 PHP2Shell 工具截图与一段利用视频流出又消失；watchTowr 随后公开确认漏洞真实并直接贴出两个 CVE 号——"我们本来都该等到周四 11 点"；PHP 因此把发布提前了一天。Daubois 的结论：泄密"严重性判断对了，但大多数细节是错的"——流传最广的那枚"php.ini 开关修复法"并不成立

### 4. LiteLLM 1.107.0 再遭供应链投毒：PyPI 版本植入凭证窃取器 + 每小时回连的后门——七个平台 wheel 全中招，上游 GitHub 仓库干净，注入点藏在 sdist 的一行 maturin 配置（HN 320 分）

**SafeDep 分析（10/21）：PyPI 上的 litellm==1.107.0 全部七个 wheel（Linux/macOS/Windows）安装后放置三个文件——cook.pth 会在任何 Python 进程启动时导入 cook.py：收集 SSH 私钥、云凭证、CI/CD secrets、AI 工具 token、浏览器密码以及 LiteLLM 代理数据库中的 LLM provider 密钥，加密后外发至 www.litellm[.]dev；sitecustomize.py 则启动后台守护进程，每小时从一个 GitHub 文件读取服务器地址、重跑窃取器并下载执行任意代码——哪怕宿主进程从未 import litellm。注入手法：sdist 包的 pyproject.toml 在 [tool.maturin] 段多出一行 data = "cook"，构建时把 cook/ 目录夹带进 wheel；上游 GitHub 源码不含这些文件。PyPI 已下架该版本，1.106.2 与 1.107.0rc1/rc2 均干净。**

**关键细节：**
- 影响面以 AI 工具链为中心：litellm 是 LLM API 网关的事实标准依赖之一（HN 读者 rcleveng："真不希望 Google ADK 把这东西塞进我的依赖树"），窃取清单里"AI 工具 token"与"代理数据库里的 provider 密钥"正是冲着 AI 开发者的钥匙串来的

### 7. LayerFS v1.0.0：给 AI 编码 agent 造的文件系统——每次工具调用挂载一个完整可写工作区、提交后即焚，"瞬态计算 + 持久共享历史"（HN 69 分）

**LayerFS（MIT 开源，v1.0.0 已发布）把 agent 的执行环境做成文件系统原语：每个 agent（或每次工具调用）在共享的提交历史上挂载一个完整、可写的 Workspace，干完活、提交变更、卸载消失——"瞬态工作区，持久结果"。设计哲学一句话：agent 约 80% 时间在思考、约 10% 在 Bash 里，于是文件操作做成对 Store 的一次原子写，每条 Bash 命令在沙箱里挂载一个临时工作区、结束后只留 commit。**

**关键细节：**
- 十条设计理念分六核心四辅助：瞬态计算（计算只在命令运行期间存在）、去中心化 agent（不同机器上的 agent 通过无服务器 Store 共享同一份历史）、每 Bash 调用一个沙箱、commit 即协作边界
- 官方宣称的目标是"把多 agent 开发的并行度扩展到想象之外"——大量 agent 各自挂载工作区、互不阻塞、在共享历史上做增量提交

### 8. GitHub 工程博客：为 agent 时代的 Git 基础设施铺桥——99.99999% 仓库的副本已迁入 Azure，剩下的用"按引用仲裁"续命：不同引用的写入吞吐提升 3-4 倍（HN 38 分）

**GitHub 披露其存储迁移的收官战役：已把 99.99999% 仓库的副本迁至 Azure，剩余仓库卡在"单一仓库写入瓶颈"上——现有架构里一次跨区域往返决定所有写入的串行化。解法是 per-reference quorums（按引用仲裁）：写入序列化只发生在单个引用（分支/tag）内部，不同引用的写入（agent 与开发者各自推各自的分支）不再互相等待、可并行在途，内部测试中不同引用的写入获得 3-4 倍吞吐与更低延迟。**

**关键细节：**
- 读侧另起一章：多数仓库读写比约 1:100 到 1:1000，今日读写打同一批副本、无法独立扩缩；方案是让对象存储成为仲裁组的特殊成员——"虚拟写入副本"作为通往 Azure Blob Storage 的桥，写入直到在对象存储中持久才算确认，再按需拉起任意数量的"虚拟读副本"
- 巧思在聚合：虚拟写入副本把落在不相交引用上的事务合并成一批网络 I/O——繁忙仓库为多次并发写入只付一次跨区域往返
- 标题里的"agent-scale"不是修辞：GitHub 明说迁移的背景负载是 agent 与开发者并行推送、互不等候——编码 agent 数量级增长直接改写了全球最大 Git 服务的存储架构路线图

**Texas Tribune（10/20）：新报告警告，若数据中心主要由燃气电厂供电，得州二十年来依靠风电光伏增长、污染控制与燃煤退役换来的空气质量进步，可能在 2031 年前被逆转——氮氧化物（NOx）排放将较当前增长 136%、回到 2004 年水平；挥发性有机化合物将超过 2002 年水平 32%；颗粒物（PM）将回到 2006 年以来未见的高度。报告作者 Carlos Gamarra："我们必须重视这件事——没人想回到 2000 年代初的排放水平。"**

**关键细节：**
- 供电方式的排放摆幅极大：数据中心自建燃气发动机的 NOx 排放约为同等规模电网供电的 4 倍；若全部新增需求都由燃烧发电满足（而非电网 + 风光配套），NOx 排放将高出 2-10 倍（取决于需求预测口径）
- 供给端已在路上：据非营利组织 Environmental Integrity Project 统计，得州目前规划中的燃气电厂至少 32 座——超过其他任何州
- 受影响的首先是本来就贴线的都会区：休斯敦、达拉斯-沃斯堡、圣安东尼奥与奥斯汀本就经常达不到联邦空气质量标准（交通排放 + 夏季高温）；报告同时强调"即便是最清洁的供电情景"，数据中心带来的区域排放增量也不可忽视
- PM 被单独点名：可深入肺部并进入血液的微粒被一些科学家称为"最致命的空气污染形式"——诱发哮喘发作、心律不齐与呼吸系统疾病
- 连续性：本报"AI 数据中心外部性"系列的新维度——此前追踪的是钱（CoreWeave CDS、银行甩卖贷款）、电（GCP 伦敦断电）与地（微软退出英国项目），今天补上空气：当"AI 电价"开始以 NOx 与 PM 计价，数据中心选址的政治经济学又多了一个变量
